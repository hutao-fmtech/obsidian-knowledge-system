# README 写作范式（自然优先）

> 先保证可读性和自然思维流，再保证内容上覆盖 What / Why / How。

## 核心原则

- 允许自然叙述，不强制写 `What`、`Why`、`How` 标题。
- 但内容必须覆盖三件事：
  - What：这是什么，边界是什么。
  - Why：为什么重要，不做会怎样。
  - How：具体怎么做，怎么流转，怎么收尾。
- README 首先是“可执行说明书”，其次才是“结构模板”。

## 必须讲清楚的三层信息

### 1) What（定义与边界）
最少回答：
- 这个目录的角色是什么。
- 什么应该放这里，什么不应该放这里。
- 与相邻目录如何区分。

建议：给 2 个正反例，避免抽象定义。

### 2) Why（价值与风险）
最少回答：
- 这个目录对系统的价值是什么。
- 如果不维护，会出现哪些具体退化信号。
- 它和上游/下游目录如何连接。

建议：用真实问题描述风险，不要只写口号。

### 3) How（动作与流转）
最少回答：
- 日/周/月的关键动作。
- 新建、分发、归档/删除的路径。
- 何时算“处理完成”（DoD）。

建议：动作尽量具体，可附 Dataview 或命令。

## 推荐写法（非强制章节名）

一个目录 README 通常包含这些内容即可：
1. 一句话定位（定义）
2. 目录边界与判断规则
3. 价值与风险
4. 流转路径与操作节奏（日/周/月）
5. 状态看板（Dataview 或检查清单）
6. 导航链接（手册、HOME、相关 README）

### 按目录类型选格式

- 知识生产目录（01/02/03/10）完整 6 章：状态看板 / 概念+区别 / 工作流 / 原则与技巧 / 创建指导 / 相关导航
- 支撑性目录（04/05/20/30/90）精简格式：概念、使用规范、相关导航，按需选取
- 风格：方法论写判断过程而非规则列表；举系统中真实存在的例子（引用系统里确实存在的笔记，而不是虚构的示例），不用占位符；工作流写到动作级别；原则每条给判断标准或具体例子
- 结构调整必须先和用户确认，不能自作主张删减或重组章节

## 质量门槛

- 读完 60 秒内能回答：这是什么、为什么、怎么做。
- 有明确流转指引（从哪里来，到哪里去）。
- 至少有 1 个状态看板（Dataview 或清单）。
- frontmatter 包含 `title`、`type`、`created`、`updated`、`tags`，字段含义以 [[00-系统/Frontmatter 规范]] 为准。
- 至少 2 个结构化 wikilinks：[[00-系统/📖 使用手册]]、[[00-系统/🏠 HOME]]。

## 反模式

- 套模板痕迹重，读起来像制度文。
- 只讲原则，不讲流转路径。
- 只有分类，没有处理节奏。
- 没有退出机制，导致目录长期积压。
